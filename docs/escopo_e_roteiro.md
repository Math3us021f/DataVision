# Escopo e roteiro do DataVision

> Este documento registra o status real de cada etapa. Não marcar uma etapa como concluída sem verificação executada.

## Escopo

DataVision Admin (primeira entrega) + módulo de análise de dados (posterior). Arquitetura: FastAPI, SQLite, MinIO, psutil, Docker/Docker Compose. Regras completas em [../CLAUDE.md](../CLAUDE.md).

## Decisões técnicas registradas

- 2026-10-24: **Reorganização de `src/` antes de iniciar o frontend.** Os 5 módulos de rota (`users.py`, `datasets.py`, `files.py`, `logs.py`, `metrics.py`) foram movidos para `src/routers/`, separados da infraestrutura (`auth.py`, `db.py`, `storage.py`, `logging_config.py`, `rate_limit.py`, `profiling.py`), que continua na raiz de `src/`. Motivo: a pasta ia crescer mais com as páginas HTML/CSS/JS do frontend, e misturar tudo no mesmo nível ficaria confuso. Suíte completa (54 testes) confirmada passando depois da reorganização, antes de qualquer código novo.

- 2026-10-24: **MinIO local de dev usa a imagem `cgr.dev/chainguard/minio`**, não `minio/minio` do Docker Hub (bloqueada para pull sem login — mudança de distribuição da própria MinIO). Mesma imagem já usada na produção Ubuntu, mas com bucket e credenciais totalmente separados (gerados agora, só para dev), nunca reaproveitando os de produção. **Atenção:** durante essa decisão, a senha real do MinIO de produção apareceu em texto puro no chat — recomendado trocá-la.

- 2026-10-24: Git inicializado neste momento (o projeto já existia sem controle de versão). Primeiro commit inclui o estado atual da Etapa 2.
- 2026-10-24: `requirements.txt` ainda sem versões fixadas (`fastapi`, `uvicorn[standard]`). Fixar versões é uma pendência antes de avançar muito no desenvolvimento, para reprodutibilidade do build.
- 2026-10-24: **Etapa 6 reduzida de escopo.** O roteiro original previa "estado de serviços e logs" de forma genérica. Avaliamos e decidimos: nesta fase (dev no Windows, sem systemd, sem acesso ao Docker via socket — proibido pelo CLAUDE.md), só implementamos leitura dos logs da própria aplicação. Status/logs de outros serviços (Docker, systemd) ficam para a fase de deploy no Ubuntu, quando journald fizer sentido de verdade.
- 2026-10-24: **Banco de dados trocado de SQLite para PostgreSQL** antes de iniciar a Etapa 3. Motivo: revisão de uma conversa externa (ChatGPT) sobre modelagem trouxe a sugestão de PostgreSQL + multi-tenant (organizações). Avaliamos e decidimos um meio-termo: adotar PostgreSQL agora (mais robusto a longo prazo, evita migração posterior), mas **sem** o modelo de organizações/multi-tenant, que fica adiado até haver necessidade real. `CLAUDE.md` seção 6 atualizado para refletir isso. Modelo de usuários continua individual (cada usuário é dono dos próprios dados), sem tabela `organizations` por enquanto.

- Porta 8000 publicada em todas as interfaces do host (aceitável em desenvolvimento local, revisar antes de qualquer exposição além da rede local).

## Pendências técnicas menores

- `TestClient`/`starlette` avisam que `httpx` está depreciado em favor de `httpx2` — trocar quando a migração for simples, não é urgente.
- Aviso de permissão ao criar cache do pytest (`/app/.pytest_cache`) dentro do container — inofensivo (diretório de cache, não afeta resultado dos testes), mas pode ser limpo depois ajustando dono do diretório.
- Sessão não tem `Secure` no cookie ainda (não há HTTPS em dev) — revisar antes de qualquer exposição além de localhost.
- Sem limite mínimo de tamanho de senha ao criar usuário — risco baixo (só admin cria usuários), mas vale um mínimo (ex: 8 caracteres) quando houver tempo.
- `src/db.py` abre uma conexão nova por requisição, sem connection pool — não é falha de segurança, pode virar gargalo de performance se o uso crescer.
- CSRF mitigado por `SameSite=Lax` no cookie de sessão, mas sem token CSRF explícito — revisar quando houver frontend HTML de verdade (Etapa 2 em diante do roteiro original previa HTML/JS simples).
- Não existe endpoint para alterar senha de um usuário existente nem editar `username`/`is_admin` depois de criado — gestão de usuários incompleta, mas fora do escopo definido nas etapas já concluídas.
- O usuário Postgres `datavision_app` (antigo dono das tabelas, ainda superusuário) permanece no banco, usado só para manutenção manual — documentar isso para quem for inspecionar o banco no futuro não se confundir com o usuário da aplicação.
- `db-init/01-create-app-role.sh` automatiza a criação do usuário limitado **só em volumes novos** (mecanismo padrão do Postgres). No volume atual do projeto, a mudança já foi aplicada manualmente via `psql` — o script existe para reprodutibilidade futura (outro dev, outra máquina, ou um reset intencional do volume), testado isoladamente num ambiente descartável antes de ser confiado.
